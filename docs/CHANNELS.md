# Sessions, Channels and Actors

## Session, Channel, and Actor Design

Caelumora uses an actor-based model for communication within sessions.

### Session and SessionLoop
A **Session** represents a high-level container for a specific interaction context. The `SessionLoop` manages multiple channels within that session.

Channels can be created in and deleted from a running session (`SessionLoop::create_channel` and `delete_channel`, `POST /sessions/{id}/channels` and `DELETE /sessions/{id}/channels/{cid}`). Every channel is a document of its own in the `EntityStore` (issue 70); the session document lists its channels by id, in order (`Session.channels`). Creating a channel stores the channel (`CreateChannel`) and then adds its id to the session through `SessionController::add_channel`, which checks `UpdateSession`, so that only the owner may do it; deleting takes it out of the session (`remove_channel`) and deletes the document (`DeleteChannel`). Only then is the running session changed and the change announced (`ChannelCreated`, `ChannelDeleted`). Creating a session stores its channels with it (`SessionTemplate::build` yields both), deleting a session deletes them, and loading a session loads them - in the runtime's name, since starting a session the caller may read must not fail on a channel the caller is not in. Each document has one writer that holds a lock while it changes and stores it: the `SessionController` the session, the `ChannelController` its channel - renaming a channel (`ChannelLoop::update_name`, checked as `UpdateChannel`) is stored first and only then taken over and announced (`ChannelUpdated`).
*   **Building a channel.** Every channel is built by `Channel::build`, from a template (`ChannelTemplate::instantiate`) or on request. It adds an approver if the channel has none - a template may name its own, with its strategy - and makes every user and agent in the channel a contributor. The participants of a requested channel come from the session's participants, the creator always among them, and its moderator defaults to `round_robin` and its confidentiality level to `session`, as in a template. A request that cannot be met - no name, a name the session already has, an unknown moderator, someone who is not a participant of the session, the level `private` - is a `SessionError`, refused before anything is stored.
*   **Running channels.** `SessionLoop::run` starts every channel in its `JoinSet`, those the session had and those created later, which it receives over a queue. Stopping the session aborts `run`, and with it every channel. Deleting a channel aborts that channel's task and deletes its state. A channel deleted while it waits to be started is never started.
*   **Changing the participants** of a running channel is an operation of the channel, not of the session (issue 46): see *Participants* below.

### Channel and ChannelLoop
A **Channel** is a specific communication medium within a session (e.g., a chat room). The `ChannelLoop` is responsible for:
*   Managing the lifecycle of **Actors** participating in the channel.
*   Routing **Envelopes** (events) between actors.
*   Applying a **Moderator** to control message flow and determine which actor speaks next.

#### Acting in a channel

Whoever writes or approves does so in their own name: `ChannelLoop::user_actor(UserId)` returns *that user's* actor, and every envelope is built by the actor itself, so sender, name and `SecurityContext` follow from it. There is deliberately no way to reach "some" user actor. Someone who is not a participant of a channel has no actor in it and is refused with `403` (issue 30). A frontend talks to the user's actor, never to the channel: the actor queues what its user writes, approves or announces, and its task sends it on through the transport `run` was given, like every actor's output - no actor takes a way around it. The queue closes when the actor's task ends, also when it is aborted with its channel, so that sending to a stopped channel fails instead of waiting. Waking the channel for a message is the actor's, too: it sends a `WakeupRequested` ahead of every message, in the message's span; neither a frontend nor the channel decides that by itself (issue 90).

#### Participants

Participants of the session can be added to and removed from a running channel (issue 46): `ChannelLoop::add_participant(ctx, participant, history)` and `remove_participant(ctx, participant)` (which stops the participant's actor through `Actor::stop`, see *Agent Cognitive Cycle*), over REST `POST /sessions/{id}/channels/{cid}/participants` (`{participant, history}`) and `DELETE …/participants/{aid}`. Like renaming, the change is made by the channel's one writer, the `ChannelController` (`add_participant`, `remove_participant`): it recomputes the channel's security attributes from its participants, stores the channel (`UpdateChannel` - only the owner) and announces `AgentChannelJoined`/`Left` or `UserChannelJoined`/`Left`. Events only announce; nothing changes a channel because an event arrived. Adding is additionally asked as `ActionType::JoinChannel` with the channel's classification, where a policy can hold the channel's level against the newcomer.

*   **History.** Whoever adds a participant decides how much of the history so far they may see: `HistoryAccess` - all (the default), none, the last n messages or the last n days. It is fixed at once as a `HistoryStart` (a message id) in `Channel::history_limits`, so "the last three days" does not move day by day. The model only holds these as data; `ChannelLoop::visible_history(participant)` is the one place they are applied - it answers with a `VisibleHistory`: the messages, the digest of the history (up to where) and the participant's start (from where), which `read_history` records together - to the history over REST, in the snapshot, for `read_history` and for the transcript of a joining agent. A joining agent gets the visible part into its transcript. One that rejoins gets only what was said after the last message it has - what it missed while away: the transcript is only appended to, so older messages that a wider grant makes visible would land after its own later answers; the agent reaches them through `read_history`, and its transcript stays in the order things were said. Notes stay visible to everyone in the channel: they are written on paper, not part of the conversation.
*   **Running.** The `ChannelLoop` starts the new actor's task (its run loop takes such changes over a queue and ends once its last actor has ended), tells the moderator and rebuilds the `MentionDirectory`; a handle that becomes ambiguous is logged as at the start. A removed actor is stopped at once - an agent without finishing its turn - and its state is kept, for the record and for a later return. The approver answers a leaving agent's pending approvals as denied, so that nothing keeps waiting, and recomputes the others, since the number of users changed. The approver itself cannot be removed.
*   **Being told.** A leave is announced on the event bus like every change of membership (issue 73). A removed user's live stream of the channel ends because it is theirs: it is followed through their actor (`UserActor::watch`), which ends when it is stopped - no one has to listen for the announcement (issue 104). Every channel response carries `can_change` (`AccessQuestions::may_change_channel`, asked when the view is built), and the web UI offers adding (with the choice of history) and removing participants in the member list only where it is set; it fetches the channel again when the global stream announces a join or leave for it. A channel its viewer may not read (`GetChannel`: owner and participants) is answered as absent and left out of lists and snapshots. The runtime decides that, not the REST server: `SessionLoop::channel_for(ctx, id)` returns a channel only to whoever may read it (`SessionError::ChannelNotFound` otherwise, the same as for one that does not exist), and the views list only those (issue 80); every REST handler reaches a channel through one `open_channel` (issue 102).

*   **Views** (issue 80). What a client lists and offers comes from the runtime as views of `caelumora_model::view`: a `SessionView` (participants and readable channels) and a `ChannelView` (members with handles and `can_read_context`, and `can_change`), each for one viewer. The `SessionManager` builds them - `session_views(ctx)`, `session_view(ctx, id)`, `channel_view(ctx, session, channel)` - for running and stopped sessions alike and without starting one: a channel is described from its `Channel` document, the running channel's or the stored one, by one private `describe_channel`, which asks the `AccessQuestions`; names are read in the runtime's name (issue 120). REST only maps views to responses (`From<ChannelView> for ChannelResponse` and the like in `models.rs`) and asks the `SecurityManager` nothing. A view is a snapshot for listing and offering: an operation checks its own permission when it acts, never by a view.

Two things act on the channel as a whole and therefore ask the `SecurityManager` first, one decision for the whole channel rather than one per actor:

*   `ChannelLoop::cancel` (`ActionType::CancelChannel`) ends the current turn of every actor — the web UI's stop button. It is an operation on the channel, like renaming or deleting it, not an act of taking part: the policy decides who may, and nobody has to be a participant for it (issue 102). It is not a kill: a running tool finishes, the agent reflects, emits `FullResponseGenerated` so observers stop waiting, and returns to a normal state with its history intact. A model call in flight is dropped, not awaited: `Actor::cancel` is synchronous, flips the agent's `ProcessingStateHolder` to `Cancelling` and cancels the turn's `CancellationToken`, on which the streaming loop waits next to the model's stream, so that the request is abandoned at once wherever it stands (issue 76). Afterwards the channel is *quiet* until it is woken - by the `WakeupRequested` a user's actor sends ahead of its next message, or deliberately: what is said is still delivered, so that every agent's transcript keeps up with the history, but nobody is asked to respond to it.
*   `ChannelLoop::wakeup` (`ActionType::WakeChannel`) is a *deliberate* wakeup, as `/wakeup` is (see *User commands*); `wakeup_actor` wakes a single actor under the same permission. Waking because something is on its way — a `WakeupRequested` an actor sends, a user's mention — happens as the channel routes it (`wake_for_delivery`) and asks nothing: it follows from an action that was already permitted, and a user allowed to write but not to wake would otherwise be unable to write.

A refusal is a `ChannelError::Forbidden`, which `caelumora_runtime::error::is_forbidden` recognises so that REST answers `403` rather than `500`; like a refused tool call, it says what was refused and not which rule refused it.


#### Channel and actor runtime

A `ChannelLoop` is built with a `ChannelRuntime`, not with the `RuntimeManager` itself. It carries what everything in the channel shares: the process-wide services of the `RuntimeManager`, the user commands of the session (a `CommandExecutor`, built once per session by `RuntimeManager::new_command_executor`) and a handle to the channel. The `ChannelRuntime` is the only source of `ActorRuntime`s, so every actor belongs to exactly one channel. The handle is a `Weak`, set once by `ChannelLoop::new` when the channel exists: the channel owns its actors, and a strong reference back would keep a stopped channel alive.

An `ActorRuntime` is made for one actor (`ChannelRuntime::new_actor_runtime(actor, session, channel)`) and hands out only what concerns it (issue 69): the services every actor needs (`security_manager`, `llm_client`, `secret_manager`, `component_registry`, `new_tool_executor`, `command_executor`), its own agent state (`agent_state`) and state in the channel (`load_channel_state` / `store_channel_state`), its personality, its own event subscription (`subscribe_channel` - its channel, nothing else) and announcement (`announce_channel_state_changed`), a narrow view of its channel (`classification`, `channel_attributes`) and a `SessionReader` that enforces the confidentiality rules. The full `ChannelLoop` and `SessionLoop` are `pub(crate)` - the user actor needs the channel for commands, the reader both - so components from other crates cannot reach them.

`ComponentContainer::from_config` takes the registry and a `ComponentContext` — the security context and the `SecretManager` of the whole graph, and the `SessionReader` of the actor the components are built for (`session_reader::detached()` for components of no actor, such as the session's commands), through which each component reaches the others it asks for. Components are not given their actor's `ActorRuntime` ([128](../issues/128-actor-runtime-in-components.md)): through it they could store the actor's state or act as the actor past the `Turn` they are called with. What a component may use at build time is exactly what `ComponentContext` holds; a new need gets its own narrow handle there, as reading other channels did.


### Actor and ActorId
An **Actor** is any entity that can send and receive events in a channel.
*   **`Actor` trait**: Defines the interface for all actors, including an `async fn run` method.
*   **`ActorId`**: Uniquely identifies an actor, which can be a `User` or an `Agent`.
*   **`Envelope`**: The unit of communication, containing a timestamp, security context, event context, and the actual `ActorEvent`.

### Moderators
Moderators control how messages are routed and who is allowed to respond. A channel's moderator is named in its template (`ChannelTemplate.moderator`, default `round_robin`) and built by `RuntimeManager::new_moderator`.

All moderators route the same way: every message goes to every other participant, approvals, failed turns and announced commands go to whom they concern, and every agent a user `@`-mentioned is asked to respond. They differ only in whom they ask when a message mentions no agent. That difference is a `ResponderPolicy`, and `PolicyModerator` is everything else (`caelumora-runtime/src/moderator_impl/`), so a new moderator is a new policy:
*   **`broadcast`**: every agent responds.
*   **`round_robin`**: the agents take turns, in the order of their ids. A mention does not take a turn.
*   **`random`**: one agent, chosen at random.
*   **`mentions_only`**: nobody. Agents respond only when a user mentions them, and a message without a mention gets no answer.

The REST API returns each channel's `moderator`. The web UI shows it above the member list, and for `mentions_only` its input field says that agents answer only when mentioned. The TUI prints it when the chat starts.

#### `@`-Mentions
A user can address participants directly with `@handle` (e.g. `@sassy` for "Sassy"). A handle is the participant's name lowercased, with every run of other characters collapsed into `-` (`caelumora_model::mention`). The `ChannelLoop` resolves mentions once, as a message enters the channel, and stores the resolved `ActorId`s in `Message::mentions`; nothing downstream re-parses the text, so a later rename cannot change whom a past message addressed. Unknown handles stay plain text, and text in backticks is ignored.

A mention changes who is asked to respond, not who receives the message: every participant still gets it, but every moderator (via the shared `ModeratorActors::mentioned_responders`) sends `ResponseRequested` to exactly the mentioned agents instead of applying its own policy. Mentioned agents that are asleep are woken first. Only mentions written by a user are routed; mentions in agent responses are resolved and rendered but do not steer the moderator, so agents cannot address each other in an unbounded loop. The REST API lists each channel's `members` in no particular order, each with its handle (`null` for participants that cannot be mentioned, such as approvers); the web UI sorts them by name and uses them for the member list, `@` completion and highlighting.
