# Agent Guidelines

Welcome, coding agent! This document is your entry point for contributing to Caelumora: the goal we
work towards, the principles of design that serve it, and how we work together. How code is written
is in [docs/CODING-GUIDELINES.md](docs/CODING-GUIDELINES.md); everything else is in [docs/](docs/),
and the table below says which document to read before working on what.

## The goal

Caelumora's code is to have the least complexity it can, and to get better with every change, not
worse. What we minimise is complexity, not effort: the size of a diff, the number of files touched
or the time a solution takes is never the argument for it. Say what a solution costs, and choose it
by what the code looks like afterwards. A change is not done when it works, but when the code around
it reads as if it had been designed with the change in mind.

### Issues

Open issues live in this repository, not in an external tracker. Every issue is a file
`issues/<number>-<slug>.md`: its field lines - status, type, priority, area, summary - and below
them the reasoning, the options that were weighed, and the decision.
[issues/INDEX.md](issues/INDEX.md) lists every issue by area, [issues/OPEN.md](issues/OPEN.md)
those open or in progress. If what you are about to do corresponds to an issue, work from that
issue's file - it usually records why an obvious approach was already rejected. In short: the issue
file is the one place its status is kept, the overviews are generated by `issues/generate.sh` and
never edited by hand, the description of a resolved issue is never rewritten (what happened goes
under `## History`), and numbers are never reused.

## Design principles

*   **The interface comes first.** A new type, trait or feature, and a change to a public
    interface, begins with the interface: the public methods with their signatures and a one-line
    doc comment each, put before the maintainer before any body is written. The interface states
    one concept: its name and its methods can be described in one sentence, without an "and also".
    If it cannot be written that way, the concept is not clear yet. Two signs that a type has to be
    split or generalised: many similar methods - differing only in the kind they handle, or in a
    flag -, behind which a generic method or a missing concept hides; and methods that touch
    different areas - each group using fields of its own, or sharing a prefix of its own -, which
    belong to several types.
*   **Follow the pattern, or change it.** Before designing, find the closest thing the codebase
    already has, name it in the plan, and build the new thing the same way: construction, naming,
    configuration, errors, where it lives (commands like tools: a `…Provider` component facet, and
    something that receives the ready providers and checks permissions - for tools the runtime's
    `ToolExecutor`, issues 127 and 280). If the pattern does not fit, question the pattern and
    propose changing it for all its uses; never add a variant beside it. Where two implementations
    of one thing differ without a reason - in naming, construction, error handling -, propose
    aligning them, in whichever direction is the better one. A deliberate difference is named with
    its reason.
*   **Existing cuts are not fixed.** Which type owns what, which crate holds what, what a concept
    is called - each may be questioned whenever a simpler design shows. If a change only fits by
    bending the existing code, propose the restructuring that makes room for it, as an architecture
    decision with what it costs, instead of building the change in somehow. Glue code that feels
    awkward - one object making another act on its behalf, a parameter that only works around
    missing ownership - is a sign that something sits on the wrong object. Simpler means fewer:
    fewer concepts a reader must know, fewer special cases (`if kind == …`), fewer parameters
    passed on only to be passed on, fewer ways of doing the same thing.
*   **Concepts are named.** Every concept has one name: the name of its type or trait in the code,
    and the word for it in the documents. A concept that exists only as a convention or a sequence
    of calls gets a name of its own. When what a concept means changes, it is renamed everywhere,
    in the same change.
*   **One owner per concern.** Every crate, module and type can be described in one sentence - for
    a module, the first sentence of its module docs; if the description of a change needs an "and
    also", something is on the wrong object. Logic that belongs together by subject lives
    together - its data, rules and checks in one place - and is not spread over crates because its
    callers happen to be there: `caelumora-model` holds data and rules, `caelumora-runtime` where
    everything runs, `caelumora-agents` what an agent does there, `caelumora-rest-server` only
    maps HTTP to the runtime (see
    [ARCHITECTURE.md](docs/ARCHITECTURE.md)). When a caller needs something an owner does not
    offer, extend the owner rather than computing it at the caller.
*   **Few generic types, not many helpers.** A new type or trait needs a responsibility of its own.
    One that only bundles parameters, wraps a single call, or serves a single call site is a sign
    that the responsibility belongs to an existing type. Before adding a trait, check whether an
    existing one can be generalised to cover the case; before adding a family of near-identical
    types, check whether one generic type would do.
*   **A clear and consistent public API.** The same concept has the same name everywhere (the
    `…_id` of what it identifies, `load_…` for loading, `…Provider` for a facet). Similar things
    are constructed, configured and fail the same way. Make visible only what is used from outside
    (`pub(crate)`, `pub(super)` by default), and do not expose internals that make callers rebuild
    logic the owner should provide.
*   **No repeated logic.** When writing something that resembles existing code - a second `match`
    over the same kinds, a second copy of a check, a conversion done again - move it to one place
    (a method of the type it is about, a shared function, a generic) before adding the second use,
    not after the third.
*   **Nothing without a user.** No parameter, option, method or trait without a caller today: a
    generic mechanism is welcome, a setting nobody sets is not. Code that a change leaves unused is
    deleted by that change.
*   **Restructure, then extend.** A refactoring that prepares a feature is a step of its own,
    without behaviour changes, so that both can be reviewed separately.

## Workflow

1.  **Read.** Before any work on code, read [CODING-GUIDELINES.md](docs/CODING-GUIDELINES.md) - in
    full, also when you believe you know it: its rules are the ones most often missed. Then read
    the documents on the subject of the work (table above), and look in
    [issues/INDEX.md](issues/INDEX.md) for an issue covering it.
2.  **Analyse.** Understand the requirement and where it belongs in the overall structure. Find
    the closest existing pattern. If the change only fits by bending the existing code, the
    restructuring comes first, as a decision of its own.
3.  **Plan.** Name the pattern you follow, write the interface of every new or changed public type,
    trait and method, and list the files and the tests. Where the work adds or changes a public
    interface or raises an architecture question, put the plan before the maintainer and wait for
    the decision.
4.  **Implement.** Make the change completely: everything it needs, nothing beside it - its tests
    included.
5.  **Document.** Update the document in `docs/` on the subject, `docs/ARCHITECTURE.md` and/or
    `README.md` where your change changes a concept, a rule or how the parts fit together; what a
    type or method does in detail goes into its doc comments. What belongs where is described in
    [CODING-GUIDELINES.md](docs/CODING-GUIDELINES.md#what-goes-where).
6.  **Self-review.** Read the whole diff as a reviewer would, and answer:
    *   Can it be simpler? For every new type, trait, method and parameter: is it needed, or could
        an existing one take its place?
    *   Where did complexity grow - a special case, a parameter passed through, a second way of
        doing something - and can it be taken back?
    *   Do the cuts still hold? Can every type and module the change touches still be described in
        one sentence? Did one of them get a method that does not fit that sentence?
    *   Does the code follow the pattern named in the plan, and the interface agreed?
    *   Does it keep the rules of [CODING-GUIDELINES.md](docs/CODING-GUIDELINES.md)? Go through
        its [checklist](docs/CODING-GUIDELINES.md#rules-for-every-change) rule by rule against the
        diff.

    Change what the answers call for. Then have the change reviewed with fresh eyes, by an agent
    that has not seen the work - in Claude Code the `reviewer` agent
    (`.claude/agents/reviewer.md`) -, telling it the issue and the pattern and interface agreed in
    the plan. What it finds in the change itself - a rule broken, a design finding, a document
    not updated - is fixed, unless it is an architecture question, which goes to the maintainer.
    What it finds in the code around the change joins your findings, with your assessment; its
    questions are answered, or passed on to the maintainer.
7.  **Verify.** Run the tests. Every test passes, as does
    `cargo clippy --workspace --all-targets`.
8.  **Record.** If the change resolves or advances an issue, update its status in the issue file
    and append a dated entry under `## History`.
9.  **Report.** Leave the change in the working tree and summarise it: what it changes, what the
    self-review simplified and what it could not, your findings (below) and the reviewer's, and
    which stored data has to be deleted, if any. Then wait for the maintainer's review.

## Working together

### Decisions

Architecture questions are discussed before they are implemented: where a method lives, which object
owns a responsibility, how context reaches the code that needs it, new types or layers, a new or
changed public interface. Lay out the options with their trade-offs, give a recommendation, and wait
for the decision. Proposals from the maintainer are to be assessed honestly, not just accepted.

The rules of this document and of `docs/` serve the goal above. Where one stands in the way of a
clean solution, present the problem and say which rule blocks it, rather than bending the solution
around the rule.

### Findings

What you come across while working that is not clean - too complex, on the wrong object, repeated,
misnamed, a pattern followed in one place and not in another - is reported: neither fixed on your
own nor built around. It goes into a section *Findings* of your summary, each with its place
(`file:line`), what is wrong, and the refactoring you propose. The maintainer decides whether it
becomes a step before the work, an issue of its own, or nothing.

### Corrections become rules

What the maintainer corrects in a review and no document states yet becomes a rule: propose its
addition to the document on its subject, in the same work. A rule that has been missed twice is not
written down more emphatically, but checked by a tool - a lint in `[workspace.lints]`, a test, a
check of the pre-commit hook -; propose the tool as a finding.

### Branches and commits

Every piece of work happens on a branch of its own, made from the current `main` and named after the
work, with the issue number if there is one (`issue-264-read-channel`); if you are already on such a
branch for the same work, keep using it. Only two things happen on `main` directly: a change the
maintainer explicitly asks for there, and opening a new issue - in a commit of its own, pushed at
once, as [issues/README.md](issues/README.md#creating-a-new-issue) describes. Changing an existing
issue - its status, its history, a decision recorded - belongs to the work on it, on its branch.

Work of several steps - a plan whose steps an issue records - is reviewed and committed step by
step: once a step is done and verified, stop and report it. Only after the maintainer has reviewed
and accepted it, commit it on the work's branch - one commit per step, so that each stays
reviewable on its own - and only then begin the next. Apart from that, commit only when asked to.
Do not push unless asked to, except a new issue.

When the work is done, ask whether the branch should be merged into `main`, and merge only after the
maintainer agreed. Before merging, update `main` from the remote repository (`git fetch`, then
fast-forward `main` to its upstream, `git merge --ff-only @{upstream}`), then merge the branch into
it. Resolve merge conflicts so that the intent of both sides is kept; where that is not clear, ask
instead of guessing. After a merge that needed conflict resolution, run the tests and
`cargo clippy --workspace --all-targets` again before reporting the merge as done.
